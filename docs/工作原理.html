CHAPTER 01

问题：入站的路被谁堵死了

家里的宽带、办公室的网络、手机的热点——绝大多数中国网络环境里，你的电脑没有公网 IP。 它躲在一个或多个 NAT（网络地址转换）设备后面，和几十上百台设备共享一个出口地址。

这带来一个不对称的事实：你主动连别人，畅通无阻；别人主动连你，无处可寻。 入站包到达运营商的 NAT 时，NAT 不知道该转给内网哪台机器，只能丢弃。

核心洞察

防火墙和 NAT 挡的是「未经请求的入站连接」。而隧道把方向反过来：内网机器主动与公网建立长连接并保持心跳， 之后所有访问都是「顺着这条已建立的连接往回流」——对 NAT 来说，这只是普通出站连接上的双向数据，一路绿灯。

CHAPTER 02

Cloudflare 隧道：一条有名字的航道

TunnelDock 站在 Cloudflare Tunnel（工具名 cloudflared）的肩膀上。它免费提供三样东西：

  1. 全球边缘节点：访客连到离他最近的 Cloudflare 节点（全球 300+ 城市），不直接碰你的电脑；
  2. 隧道这个"账号资产"：每条命名隧道有 UUID，注册在你的 Cloudflare 账号里，持久存在；
  3. 免费 TLS 证书：HTTPS 在边缘终结，自动签发续期——你什么都不用配。

⑤ 落地

为什么地址永远不变？因为变的是"连接"（断了重连就好），不变的是"隧道 UUID + 域名记录"—— 边缘永远按 UUID 找连接，跟地址无关。而免费的临时隧道（Quick Tunnel）没有自己的名字， 每次连接分配一个随机子域，断开即回收——这就是它地址天天变的根本原因。

QUIC 与 http2：两种航道底质

cloudflared 与边缘之间默认走 QUIC（基于 UDP），低延迟、抗丢包。但有些网络（典型如部分移动宽带） 会干扰 UDP。TunnelDock 的对策：QUIC 连不上时，第二次重连自动切换 http2（基于 TCP）—— TCP 走的是浏览网页同款通道，几乎不可能被单独掐死。切换成功后记住偏好，之后直接走 TCP。

CHAPTER 03

裸隧道为什么不能直接用：PIN 门禁的五脏

Cloudflare 隧道只解决「可达」，不解决「可信」。一条裸隧道等于把你电脑上的服务直接裸奔到公网—— 全网扫描器几小时内就会找上门。所以 TunnelDock 在 cloudflared 和你的服务之间，放了一道自己造的门：

公网区 · 谁都能敲门
TunnelDock 网关区 · 第一道门
本机服务区 · 第二道门（服务自身的账号体系，如有）

127.0.0.1:端口只能经网关到达

① 口令墙：登录页 + 会话 Cookie

未认证的请求一律收到一张登录页（输 PIN）。验证通过后发放 HttpOnly + SameSite=Strict 的 会话 Cookie，12 小时免重复输入。口令比对用的是常量时间比较——连"响应快慢"这种侧信道都不给攻击者留。

② 限速：让爆破者排队

同一 IP 在 60 秒窗口内错 5 次，封锁 60 秒并返回 429。算一笔账：8 位数字 PIN 有一亿种组合， 即使不限速按每秒 10 次猜也要 116 天；有了限速（每分钟最多 10 次），需要十九年。 这也是为什么"PIN 别短于 8 位"写在手册页脚。

③ WebSocket 透传

现代 Web 应用的流式输出（AI 对话、终端、日志）都走 WebSocket。网关在 HTTP 升级握手时同样验票， 通过后把 TCP 流原样对接——只验一次票，之后当透明管道，不解析不缓存。

④ 来源头清洗：让"挑剔"的服务以为是本机在访问

很多服务（各类 agent 控制台尤其常见）自带Host/Origin 围栏：校验请求的 Host 和 Origin 是否同源， 以防 DNS 重绑定攻击。但经隧道访问时，浏览器发的 Origin 是公网域名、转发到本机时 Host 变成了 127.0.0.1——两者不一致，服务直接 403 拒绝（症状：页面打得开、一点按钮没反应）。 网关的解法：转发前剥掉 Origin/Referer/Sec-Fetch-Site 并重写 Host——信任判断已经由 PIN 承担， 上游不必再看这些可伪造的头。

⑤ 令牌引导：代拿一次性门票

少数服务（如 dsh web）还有第二道自有门禁：首次访问必须在地址栏带一次性 ?token=， 换到它自己的会话 Cookie。这个 token 只在服务日志里打印。令牌引导功能让网关在收到这类 401 时， 自动去指定日志文件里捞最新一条 token 替你带上——token 轮换也每次现读，永远跟上。

CHAPTER 04

自愈：没人值守时的求生本能

隧道类工具最大的体验杀手是「不知道什么时候断了」。TunnelDock 给每个发布配了一套状态机 idle → starting → ready error，和四条自愈规则：

故障自愈动作
隧道断线（QUIC 被掐 / 网络抖动）按 5s → 15s → 60s 指数退避重连；连续失败自动切 http2（TCP）并记住
网关进程崩溃独立监督者发现后走同一条重连链路重建（崩溃原因常见为异常断开，已加流错误兜底）
电脑重启登录时静默启动（--hidden），错峰恢复所有「自启」标记的发布
渲染界面崩溃主进程检测到后自动重载窗口，后台服务不受影响
工程细节两枚

① 网关跑在 Electron 的 utilityProcess 里——独立进程，崩了不拖垮主程序；② 对上游禁用连接复用 （agent:false）——避免"断开的旧连接"污染下一个请求。两条都是从真实故障里换来的。

诚实的边界

这不是企业级方案：PIN 是单因素认证，无审计日志，限速针对单 IP。它适合个人与小团队把 「值得保护但非绝密」的服务开到公网。Web 终端、生产数据库这类目标，请再叠加服务自身的强认证， 或者——干脆别开。

EPILOGUE

结语：三个设计决定

  1. 站在巨人背上，只造巨人不造的东西。打洞交给 Cloudflare（免费、全球、可信）， TunnelDock 只做它不做的：鉴权、适配、自愈。92MB 的安装包里，真正的自研代码只有 60KB。
  2. 默认安全，而不是可选安全。PIN 墙、限速、回环监听全是默认行为，没有「关掉保护」的开关—— 因为可选的安全迟早会被方便性牺牲掉。
  3. 把每一次故障变成一层免疫力。IPv6 陷阱、QUIC 封锁、DNS 抽风、来源头围栏—— 每个真实故障最后都沉淀为自动行为或排障口诀。软件的健壮性不是设计出来的，是这么长出来的。
